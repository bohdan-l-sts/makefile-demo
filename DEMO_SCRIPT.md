# Сценарий демо: Makefile в Laravel

Шпаргалка докладчика к «Makefile в Laravel-проектах: от „у меня всё работает" до идеального DX».
Что где лежит, см. [README.md](README.md).

---

## Подготовка перед лекцией (за день / за час)

Интернет на площадке может подвести. Всё тяжёлое скачиваем заранее:

```bash
cd app               # из корня репозитория makefile-demo
git checkout main
make init          # скачает образы php/mysql/node и vendor/, поднимет стек
make assets        # скачает node_modules и соберёт фронт
make -j3 check     # прогреет PHPStan/Pint/тесты
make down
```

Перед самим выступлением:

```bash
cd app               # из корня репозитория makefile-demo
make down
git checkout step-0
```

Шрифт в терминале: крупный (18–20pt). Отключите уведомления.

## Сценарий live demo

Шаги лежат в ветках `step-0` … `step-4` (`main` = `step-4`). Все команды ниже выполняются в `app/`.
Слайды, сниппеты и этот файл есть в каждой ветке, так что после `checkout` ничего не пропадает.
Между шагами: `git checkout step-N`. Если контейнеры уже подняты от другого шага, сделайте `docker compose down` (Dockerfile между шагами отличается).

### Общий порядок

| Блок | Что показываем | Время |
|---|---|---|
| Слайды 1–4 | вступление и «музей боли»: хост против Докера, права, гирлянды, бесяшки | 5 мин |
| Демо step-0, step-1 | боль вживую, первая попытка с Makefile | 5–6 мин |
| Слайды 5–8 | make как решение, как он думает, ловушки (+ `snippets/01…04`), план шагов | 6–7 мин |
| Слайды 9–10 + демо step-2 | фундамент | 5–7 мин |
| Слайды 11–13 + демо step-3 | продвинутое (слайды и демо вперемешку) | 7–9 мин |
| Слайды 14–15 + демо step-4 | идеал и CI | 4–6 мин |
| Слайды 16–18 | границы (+ `snippets/05`), итоги, вопросы | 5 мин + вопросы |

В каждом шаге ниже: **Подводка** (что сказать перед переключением), команды, **Что объяснить** (по каждой фиче шага) и **Переход** (мостик к следующему блоку). Подводки это не текст для зачитывания, а мысль, которую надо донести своими словами.

### Слайды 1–4 → step-0

**Переход со слайда 4:** «Всё это звучит знакомо, но давайте не на слайдах, а на живом проекте. Вот типичный Laravel-проект: Docker в нём есть, а удобства нет».

Переключаемся в терминал, `git checkout step-0`.

### step-0: «Музей боли» (2–3 мин)

**Подводка:** «Это проект, в который вы пришли в первый день. Docker-compose есть, README есть. Посмотрим, что нас просят сделать».

```bash
git checkout step-0
cat README.md                         # README приложения (app/README.md), не этот сценарий: 11 шагов, PHP и Node на хост, «спросите Васю»
docker compose up -d --build
docker compose exec app php artisan make:model Post
ls -l app/Models/Post.php             # root root → IDE не даст сохранить
docker compose exec app rm app/Models/Post.php
docker compose down
```

**Что объяснить:**

- **README из 11 шагов.** Половина шагов ставит PHP 8.4 с расширениями, Composer и nvm *на хост*, хотя рядом лежит `docker-compose.yml`. Обратите внимание зала на «последнее обновление: полгода назад» и «спросите Васю»: документация стареет быстрее кода, потому что её никто не запускает.
- **Почему все тащат PHP на хост.** Команда `docker compose exec app php artisan make:model Post` длинная, её никто не помнит, и её надо набирать на каждое действие. Проще поставить PHP локально, и вот мы снова получили «у меня 8.2, в проде 8.4».
- **Файлы от root.** В `docker/php/Dockerfile` нет `USER`, контейнер работает от root, и всё, что он создаёт в смонтированной папке (модели, миграции, `vendor/`, кэши), принадлежит `root:root`. IDE не может сохранить файл → `sudo chown -R` или, хуже, `chmod -R 777 storage/`.
- **Мелочи из `docker-compose.yml`, которые выстрелят позже:** `depends_on: [db]` без healthcheck (приложение стартует раньше, чем MySQL готов принимать соединения), порт MySQL наружу `33066` (рождает второй `.env` «для хоста»), `php artisan serve` в CMD (не стартует без `vendor/`, то есть на свежем клоне контейнер сразу падает).

**Тезис:** Docker есть, но пользоваться им неудобно, поэтому все тащат PHP на хост.

**Переход к step-1:** «Первая естественная реакция любого из нас: давайте завернём длинные команды в Makefile. Так делают почти все, и почти все наступают на одни и те же грабли».

### step-1: «Makefile как свалка алиасов» (3 мин)

**Подводка:** «Вот Makefile, который появляется в проекте через неделю после жалоб. Выглядит разумно».

```bash
git checkout step-1
cat Makefile
make -n test                          # -n: dry run, показывает команды, ничего не запускает
mkdir test && make test               # make: 'test' is up to date.  ← нет .PHONY
rmdir test
echo "hello" >> storage/logs/laravel.log
make logs                             # tail: cannot open 'laravel.log' ← `cd` потерялся
```

**Что объяснить:**

- **Что стало лучше.** Команды живут в репозитории, а не в истории bash и личных заметках. `make test` короче и одинаков у всех.
- **`make -n`** (dry run): печатает команды, ничего не выполняя. Первый инструмент отладки любого Makefile, пригодится дальше.
- **Ловушка №1: нет `.PHONY`.** make по умолчанию считает, что цель это *имя файла*. Появилась папка или файл `test` (достаточно, чтобы какой-нибудь инструмент или коллега создал её), и make говорит «`test` is up to date», ничего не запуская. Тесты «прошли», хотя не запускались. Лечится объявлением `.PHONY: test`.
- **Ловушка №2: каждая строка рецепта запускается в отдельном shell.** `cd storage/logs` отработал в первом процессе и умер вместе с ним; `tail` запускается во втором, из корня проекта. Лечится `cd dir && команда` в одну строку (или путём без `cd`).
- **Чего тут ещё нет (и почему это проблема):** контейнер всё ещё от root, `.env`, ключ и миграции новичок по-прежнему делает руками по README, никакой справки (что вообще есть в Makefile?), аргументы передать нельзя.

**Тезис:** алиасы уже лучше истории bash, но у make свои правила, и их надо знать.

**Переход к слайдам 5–8:** «Почему так вышло? Потому что make это не bash-скрипт с короткими именами. У него своя модель: цели, зависимости, файлы. Давайте за пять минут разберёмся, как он думает, и тогда остальное будет очевидно».

### Слайды 5–8 (теория и ловушки)

- **Слайд 5 (make как единый CLI-слой):** акцент на том, что make уже стоит везде и сам ничего не требует, в отличие от composer scripts или npm scripts.
- **Слайд 6 (цель · зависимости · рецепт):** здесь можно показать `snippets/04-file-targets` (три запуска подряд: первый собирает, второй «up to date», после `touch` снова собирает). Это фундамент для step-3.
- **Слайд 7 (ловушки):** живьём `snippets/01-tabs` (missing separator), `snippets/02-phony` и `snippets/03-one-shell-per-line`. Вторая и третья ловушки зал уже видел в step-1, теперь он понимает *почему*.
- **Слайд 8 (путь демо-проекта):** «step-0 и step-1 вы видели. Дальше чиним по слоям: сначала фундамент, потом скорость, потом строгость».

**Переход к step-2:** «Начнём с фундамента. Цель шага: новичок делает `git clone` и одну команду, а файлы в проекте принадлежат ему, а не root». Показываем слайды 9–10 как карту, потом переключаемся в терминал и доказываем каждый пункт.

### step-2: «Фундамент» (5 мин)

**Подводка:** «Представим, что я новичок и только что склонировал проект. Сотру всё, что накопилось, кроме скачанных зависимостей, чтобы не ждать интернет».

```bash
docker compose down -v                # -v: удалить и том с базой, чтобы init мигрировал с нуля
git checkout step-2
git clean -fdxq -e vendor -e node_modules  # «свежий клон», но без повторного скачивания
make                                  # авто-справка из комментариев ##
make init                             # .env, контейнеры, composer, ключ, миграции, сиды
make init                             # второй раз: APP_KEY не меняется, сидер не падает
make artisan C="make:model Post -m"
ls -l app/Models/Post.php             # вы, а не root: UID/GID проброшены в образ
rm app/Models/Post.php database/migrations/*_create_posts_table.php
make test C="--filter=UserTest"
```

**Что объяснить:**

- **Авто-справка (`make` без аргументов).** `.DEFAULT_GOAL := help`, а цель `help` грепает в Makefile строки вида `цель: ## описание` и печатает их таблицей. Документация живёт рядом с кодом команды, поэтому не стареет: добавил цель с `##`, она сразу в справке. Это и есть замена README из 11 шагов.
- **`.PHONY` для всех командных целей.** Ловушка из step-1 закрыта раз и навсегда.
- **UID/GID.** `UID ?= $(shell id -u)` берёт id пользователя хоста, `export` отдаёт его в окружение `docker compose`, а тот передаёт в образ как build args. В Dockerfile создаётся пользователь `app` с тем же UID/GID, и контейнер работает от него (`USER app`). Итог: `ls -l` показывает вас, а не root. `?=` значит «если не задано снаружи», так что в CI или на macOS можно переопределить.
- **Почему не `docker compose exec -u $(id -u)`.** У такого UID нет пользователя внутри контейнера: нет HOME, composer не может писать кэш, git ругается. Пользователь, созданный в образе, решает это правильно.
- **`.env` как файловая цель.** Цель `.env:` это файл. Если его нет, make копирует `.env.example`; если есть, ничего не делает. Специально *без* зависимости от `.env.example`: иначе любое изменение примера перезатрёт ваш локальный `.env`.
- **`make init` идемпотентен** (поэтому запускаем дважды):
  - `.env` создаётся только один раз (файловая цель);
  - `key:generate` вызывается только если в `.env` ещё нет `APP_KEY=base64…` (`grep -q … ||`). Иначе повторный init менял бы ключ, и слетали бы сессии и всё зашифрованное;
  - `DatabaseSeeder` проверяет, есть ли уже тестовый пользователь, поэтому второй `migrate --seed` не падает на дубликате email.
- **`up` ждёт базу.** `docker compose up -d --build --wait` плюс healthcheck MySQL в `docker-compose.yml` и `depends_on: condition: service_healthy`. Миграции не стартуют, пока MySQL не готов, никаких `sleep 10`.
- **CMD в Dockerfile сменился на `php -S … -t public`.** Встроенный сервер PHP поднимается даже без `vendor/`, поэтому `up --wait` проходит на свежем клоне, и `init` уже внутри контейнера делает `composer install`.
- **Порт MySQL больше не торчит наружу.** Всё ходит внутри docker-сети, второй `.env` «для хоста» не нужен и конфликта с локальным MySQL на 3306 нет. Порт приложения настраивается: `${APP_PORT:-8088}`.
- **`TTY := $(shell [ -t 0 ] || echo -T)`.** Если stdin не терминал (CI, пайп), к `exec` добавляется `-T`, иначе он падает с «the input device is not a TTY». Один Makefile работает и у человека, и в CI.
- **Аргументы через `C=`.** `make artisan C="make:model Post -m"`, `make test C="--filter=UserTest"`. Работает, но неудобно; к этому вернёмся в step-4.
- **`logs` починен:** путь целиком в одной команде, без `cd`.

**Тезис:** одна точка входа (`make`), онбординг одной командой, которую не страшно повторить, файлы принадлежат вам.

**Переход к step-3:** «Фундамент есть. Но `make init` каждый раз гоняет `composer install`, Node всё ещё нужен на хосте, а проверки идут по очереди. Дальше используем то, ради чего make вообще придумали: граф зависимостей и время изменения файлов». Переходим на слайд 11.

### step-3: «Продвинутое» (5–7 мин)

Здесь удобно чередовать: слайд 11 → первый блок команд, слайд 12 → `make dev`, слайд 13 → проверки и база.

**Подводка (слайд 11):** «Помните `snippets/04`: make сравнивает время изменения файлов. Применим это к зависимостям».

```bash
git checkout step-3
make init                             # composer.lock изменился при checkout (добавили larastan) → install сам
make -n init                          # второй раз composer install не нужен: vendor свежее composer.lock
touch composer.lock && make -n init   # а теперь нужен: make сравнил время файлов
```

**Что объяснить:**

- **`vendor/autoload.php: composer.json composer.lock`.** Файловая цель: `composer install` запускается, только если `vendor/autoload.php` нет или он старше любого из двух файлов. После install делаем `touch $@` (`$@` = имя цели), потому что composer не всегда перезаписывает autoload.php, а нам нужна свежая отметка времени.
- **Почему install «сам» после checkout.** В step-3 добавили `larastan/larastan` в `composer.json`; `git checkout` обновил `composer.lock`, он стал новее `vendor/autoload.php`, и make понял, что зависимости надо доставить. Никто не должен помнить «после пула сделай composer install».
- **Обе зависимости важны:** частая ошибка в чужих Makefile зависеть только от `composer.lock` и пропустить ручную правку `composer.json`.
- **`make -n init`** доказывает это без ожидания: в выводе нет строки с `composer install`. После `touch composer.lock` она появляется.
- **Тот же приём для npm:** `node_modules/.package-lock.json` npm сам переписывает при каждом install. Это бесплатный маркер «node_modules актуальны», ничего трогать не надо. `$(wildcard package-lock.json)` делает lock-файл необязательной зависимостью.

**Подводка (слайд 12):** «Теперь прощаемся с nvm».

```bash
make dev                              # Vite в контейнере на :5174, Ctrl+C
```

- **Сервис `node` в `docker-compose.yml`** с `profiles: ["node"]`: он не стартует при обычном `up`, только когда его явно зовут через `docker compose run --rm node …`. Образ `node:22-alpine`, так что версия Node зафиксирована в репозитории, а не у каждого в nvm.
- **Он тоже запускается от вашего UID/GID** (`user: "${UID}:${GID}"`), поэтому `node_modules/` и `public/build/` ваши. npm-кэш переведён в `/tmp/.npm`, потому что у этого UID нет домашней папки в контейнере.
- **Нативные модули собираются под Linux:** больше нет «node_modules собраны на macOS, в контейнере падает esbuild/rollup» (слайд 4).
- **`dev` зависит от маркера** `node_modules/.package-lock.json`: первый `make dev` сам поставит пакеты. В `vite.config.js` Vite слушает `0.0.0.0:5174` (иначе из контейнера его не видно), а браузеру HMR говорит идти на `localhost`.
- **`make down` теперь `docker compose --profile node down`,** чтобы гасить и node-контейнер.
- Ещё есть `make assets`: production-сборка фронта тем же контейнером.

**Подводка (слайд 13):** «Проверки качества. Pint, PHPStan и тесты независимы друг от друга, так зачем ждать их по очереди?»

```bash
time make check                       # последовательно, ≈3 с
time make -j3 check                   # параллельно ≈1.3 с, вывод не перемешан (--output-sync)
echo n | make db-fresh                # защита от дурака
make db-dump && ls -lh storage/dump.sql
make doctor
```

- **`check: lint stan test`.** У цели `check` три зависимости и почти пустой рецепт. Без флагов make выполняет их по очереди; с `-j3` параллельно, потому что make знает, что они не зависят друг от друга. Это граф зависимостей в действии, bash-скрипт так не умеет без ручной возни с `&` и `wait`.
- **`--output-sync=target`.** Без него вывод трёх процессов перемешивается построчно и читать его невозможно. С ним make буферизует вывод каждой цели и печатает её блоком. Флаг есть только в GNU make 4+, на macOS стоит 3.81 (2006 г.), поэтому он включается через проверку `$(.FEATURES)`, а не безусловно.
- **`EXEC_T` (всегда `-T`) для проверок:** параллельные задачи не могут делить один терминал, поэтому им TTY не выдаём вовсе.
- **В step-3 добавились `lint` (Pint в режиме `--test`) и `stan` (PHPStan с Larastan, конфиг `phpstan.neon`, level 5).**
- **`db-fresh` с подтверждением.** Красное предупреждение, затем `printf 'Continue? [y/N] '; read ans`. На `n` (или пустой Enter) рецепт завершается с ошибкой, и make не доходит до `migrate:fresh`. `make: *** [db-fresh] Error 1` в выводе это и есть ожидаемый отказ. `FORCE=1 make db-fresh` пропускает вопрос (для скриптов). Почему `printf` + `read`, а не `read -p`: рецепты по умолчанию исполняет `/bin/sh`, в Ubuntu это dash, и `-p` там нет.
- **`db-dump` без паролей на хосте.** Команда выполняется внутри контейнера `db` и берёт логин и пароль из *его* окружения (`$$MYSQL_USER`, `$$MYSQL_PASSWORD`; двойной `$$` значит «это переменная shell, а не make»). Пароль передаётся через `MYSQL_PWD`, а не `-p…`, поэтому не светится в `ps`. Никакого `include .env` (почему он опасен, покажем в `snippets/05`).
- **`make doctor`.** Проверяет хост: есть ли docker, compose v2, запущен ли демон и есть ли права, свободны ли порты 8088/5174 (только если наши контейнеры ещё не подняты, иначе порты заняты нами же). Это первое, что просим запустить у новичка, у которого «ничего не работает».
- **`logs` стал одной строкой с `cd … &&`** и не падает, если лога ещё нет.

**Тезис:** make делает только нужную работу (инкрементальность), делает её параллельно и защищает от опасных команд.

**Переход к step-4:** «Это уже хороший Makefile. Осталось три вещи: сделать его строгим, чтобы ошибки не проглатывались молча; сделать аргументы человеческими, без `C="…"`; и заставить CI запускать ровно то же самое». Переходим на слайд 14.

### step-4: «Идеал» (3–5 мин)

**Подводка (слайд 14):** «Сначала строгий режим, его не видно в демо, но он ловит ошибки, которые иначе прошли бы молча. Потом аргументы».

```bash
git checkout step-4
make artisan migrate:status           # позиционные аргументы (двоеточие не ломает make)
make test UserTest                    # = --filter=UserTest
```

**Что объяснить:**

- **Строгий shell:** `SHELL := bash` и `.SHELLFLAGS := -eu -o pipefail -c`. `-e` останавливает рецепт на первой ошибке, `-u` ругается на неопределённые переменные, `pipefail` делает ошибкой упавшую команду *в середине* пайпа. Пример прямо в этом шаге: `db-dump` теперь пишет `mysqldump | gzip > storage/dump.sql.gz`. Без `pipefail` упавший mysqldump дал бы «успешный» пустой архив.
- **`.DELETE_ON_ERROR:`** Если рецепт файловой цели упал на середине, make удалит недописанный файл. Иначе в следующий раз он счёл бы битый файл свежим и не пересобрал бы его.
- **`--warn-undefined-variables`:** опечатка в имени переменной make-а (например, `$(EXCE)`) раньше тихо превращалась в пустую строку. Теперь предупреждение. Поэтому все необязательные переменные (`C`, `FORCE`, `ARGS`) явно объявлены через `?=`.
- **`--no-builtin-rules` и пустой `.SUFFIXES:`** отключают десятки встроенных правил make для C-компиляции: меньше сюрпризов и меньше шума в `make -d`/`--trace`.
- **Позиционные аргументы.** `make artisan migrate:status` make видит как *две цели*: `artisan` и `migrate:status`. Решение:
  - если первая цель из списка `PROXIES` (`artisan composer test npm`), всё остальное из `$(MAKECMDGOALS)` складываем в `ARGS` и передаём команде;
  - а чтобы make не пытался собрать «цель» `migrate:status`, объявляем catch-all правило `%: ; @:` (подходит под любое имя и ничего не делает). Оно включается только для прокси-целей, так что опечатка `make tset` по-прежнему честно падает.
- **`make test UserTest`** превращается в `--filter=UserTest` (`$(if $(ARGS),--filter=$(ARGS))`); флаги по-прежнему можно передать через `C="--stop-on-failure"`.
- **Добавилась `make npm …`** (любая npm-команда в контейнере), по той же схеме.

**Военная история** (реальная, из нашего проекта): первая версия позиционных аргументов объявляла их
в `.PHONY`, и `make artisan migrate:status` падал с `multiple target patterns. Stop.`, потому что
make прочитал двоеточие как «цель: зависимость». Фикс: catch-all правило `%: ; @:`.

**Подводка (слайд 15):** «И последнее: один источник правды для людей и CI».

```bash
cat .github/workflows/ci.yml          # CI зовёт `make ci`: те же цели, что и локально
cp Makefile.local.example Makefile.local   # личные алиасы, в git не попадают
```

- **`make ci` = `make init` + `make -j3 check`.** Workflow GitHub Actions состоит из двух шагов: checkout и `make ci`. Никаких `setup-php`, `setup-node`, кэшей composer: на раннере уже есть Docker и make. Если CI красный, вы воспроизводите ровно то же локально одной командой. TTY-проверка из step-2 тут и пригождается: в CI нет терминала, и `-T` подставится сам.
- **`-include Makefile.local`.** Дефис значит «если файла нет, молча пропустить». Файл в `.gitignore`. Туда кладут личное: другой `APP_PORT`, свои алиасы (`tinker: ; $(EXEC) php artisan tinker` из примера). Никто не правит общий Makefile под себя и не ловит конфликты в git. Новые цели из `Makefile.local` с `##` сразу появляются в `make help`, потому что help грепает весь `$(MAKEFILE_LIST)`.
- **README приложения** (`cat README.md`) теперь сводится к `make doctor`, `make init`, `make`. Сравните с README из step-0.

**Тезис:** строгий режим ловит ошибки, позиционные аргументы делают команды естественными, CI запускает то же, что и люди.

## Что поправлено относительно черновика из Gemini

| Было | Проблема | Стало |
|---|---|---|
| `.env:` → `php artisan key:generate` | запускает PHP на хосте, а смысл доклада как раз в том, чтобы его там не было | ключ генерируется в контейнере, и только если его ещё нет |
| `init` всегда делает `key:generate` | повторный `make init` меняет APP_KEY → слетают сессии и шифрованные данные | `grep -q '^APP_KEY=base64' .env \|\| …` |
| `ifneq (",$(wildcard .env)")` | синтаксическая ошибка: кавычка часть строки, условие всегда истинно | `ifneq (,$(wildcard .env))`, а лучше вообще не `include .env` (см. `snippets/05`) |
| `db-dump` берёт пароль из `.env` через `include` | кавычки и `$` в значениях ломаются, пароль светится в `ps` | креды из окружения самого контейнера БД, `MYSQL_PWD` |
| `read -p "…"` | в `/bin/sh` (dash в Ubuntu) нет `-p` | `printf …; read ans`, либо `SHELL := bash` |
| `echo "\033[…"` | `echo` по-разному понимает escape-коды в sh/bash | `printf` |
| `$(MAKE) -j3 lint phpstan test` | вывод трёх процессов перемешивается | `check: lint stan test` + `make -j3` + `--output-sync=target` |
| `docker compose exec -u $(id -u)` | у UID нет пользователя в контейнере: без HOME, у composer проблемы с кэшем | пользователь создаётся в образе с нужным UID/GID (build args) |
| `touch vendor/autoload.php` от `composer.lock` | ок, но забыли `composer.json` | зависимость от обоих файлов |

## Идеи сверху (добавлено в демо)

- `make doctor`: проверка хоста (docker, compose v2, свободные порты).
- `TTY := $(shell [ -t 0 ] || echo -T)`: один Makefile работает и в терминале, и в CI.
- Node в контейнере (`make dev`, `make assets`, `make npm …`): nvm больше не нужен.
- `node_modules/.package-lock.json` как «бесплатный» маркер для инкрементального `npm install`.
- Строгий режим: `SHELL := bash`, `.SHELLFLAGS := -eu -o pipefail -c`, `.DELETE_ON_ERROR:`,
  `--warn-undefined-variables`.
- `-include Makefile.local`: личные настройки без конфликтов в git.
- `make ci` = то, что делает GitHub Actions. Единая правда для людей и CI.
- `make -n` (dry run), `make -p` (всё, что make знает), `make --trace` (почему цель пересобирается).

## Ответы на вопросы из зала

- **Windows?** Работаем в WSL2 (там make есть), проект лежит в файловой системе Linux, а не в `/mnt/c`, иначе всё медленно.
- **macOS?** Там GNU make 3.81 (2006 г.): нет `--output-sync`, нет `.ONESHELL`… Поэтому в демо стоит проверка `$(.FEATURES)`. Либо `brew install make` → `gmake`.
- **Почему не bash-скрипт `./run.sh`?** Нет графа зависимостей, нет инкрементальности, нет `-j`, всё это пришлось бы писать руками.
- **Почему не composer scripts / npm scripts?** Для их запуска уже нужен PHP/Node на хосте.
- **А Sail?** Sail это тоже обёртка, но только для Laravel и без зависимостей между целями. Makefile может звать Sail внутри.
- **Just / Task (go-task)?** Хорошие альтернативы без легаси make, но их надо ставить. make уже есть везде.
- **Когда Makefile плох?** Сложная логика (циклы, JSON, ветвления) → выносите в `scripts/*.sh` и зовите из make.
