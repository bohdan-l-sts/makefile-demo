Как перестать мучить хост-систему, права файлов и длинные команды

Всем привет. Сегодня про DX (Developer Experience): сколько времени и нервов мы теряем, чтобы просто запустить проект, прогнать тесты или сбросить базу. Начну с живой боли, потом покажу, как один файл закрывает большую часть этих проблем.

Лайфхак для старта: открыть терминал и начать набирать длинную команду docker compose exec -it app php artisan migrate:fresh --seed… «ой, контейнер не поднят… ой, .env нет».

Музей боли · 1Хост против Докера

  • PHP 8.2 на хосте, PHP 8.4 в контейнере: «а у меня локально работает»
  • Node на хосте, у каждого своя версия через nvm: у одного 18, у другого 22
  • composer install на хосте: не те расширения → --ignore-platform-reqs → сюрпризы на проде
  • «Зачем нам Докер, если я всё равно всё запускаю локально?»
Классика: подняли Docker, но чтобы запустить composer или artisan, половина лезет в контейнер через exec, а вторая ставит PHP на хост. Версии расходятся, профит от изоляции умножается на ноль. Это не выдумка: у нас в команде на ноутбуке с PHP 8.2 проект на 8.4 без Docker просто не запускается.

Музей боли · 2Права, гирлянды, онбординг

  • Файлы от root:root → IDE не сохраняет → sudo chmod -R 777 storage/
  • Команды-гирлянды: docker compose exec -u sail app php artisan test --filter=UserTest
  • Команды живут в истории bash, в личных заметках и в чужих Run Configurations
  • README на 15 страниц, устаревший прошлым летом. «Спросите Васю». Вася уволился
Запустил генерацию миграции из-под root в контейнере, и всё: PhpStorm не даёт редактировать, git ругается. Новичок первый день не пишет код, а поднимает окружение по README, который никто не обновлял.

Отсылка к демо step-0 (его показали в начале): make:model в контейнере → ls -l показывал root.

Музей боли · 3Ещё бесяшки

  • Два .env в голове: DB_HOST=db для контейнера, 127.0.0.1:33066 для хоста
  • Порт 3306 занят локальным MySQL, который «когда-то ставил для другого проекта»
  • node_modules собраны на macOS → в Linux-контейнере падает esbuild/rollup (нативные бинарники)
  • git-хуки (Pint, GrumPHP) требуют PHP на хосте
  • Xdebug настроен на хосте, а код крутится в контейнере
  • CI запускает одни команды, разработчики другие → «в CI зелёное, у меня красное»
Спросить зал: кто узнал себя хотя бы в трёх пунктах? Общий корень: нет единой точки входа, и каждый разработчик собирает своё окружение сам. Отсюда переход к демо step-1: «завернём всё в Makefile».

Решениеmake как единый CLI-слой проекта

  • Один интерфейс: make init, make test, make check
  • Есть в Linux/macOS/WSL2 из коробки, сам не требует PHP/Node/Python
  • Прячет кишки: разработчику не нужно помнить флаги Docker Compose
  • Это не просто алиасы, а граф зависимостей с инкрементальностью

На хосте остаются только Docker и make.

Разработчику всё равно, что под капотом: Docker, Sail, OrbStack. Он знает 3–4 команды. И тот же набор команд работает в CI. Это и есть Single Source of Truth.

Как думает makeЦель · зависимости · рецепт

report.txt: data.csv        # цель: зависимости
	wc -l data.csv > report.txt  # рецепт (строго TAB!)

test:                        # «фальшивая» цель, это не файл
	php artisan test
.PHONY: test
  • Цель = файл. Пересобирается, если его нет или зависимость новее
  • .PHONY = «это команда, а не файл»: выполнять всегда
  • make -n показывает, что будет сделано, ничего не запуская
make придумали в 1976 для компиляции C: не пересобирать то, что не менялось. Эта же идея даёт нам «composer install только когда поменялся composer.lock».

Демо: snippets/04-file-targets: make, make ещё раз (up to date), touch data.csv, make.

ЛовушкиТо, на чём спотыкаются все

  • TAB, не пробелы: иначе missing separator. Stop.
  • Нет .PHONY: появилась папка test/ → 'test' is up to date
  • Каждая строка рецепта отдельный shell: cd и переменные не доживают до следующей
  • $ в рецепте это make, а $$ это shell
  • /bin/sh в Ubuntu это dash: нет read -p, echo -e ведёт себя иначе → printf
  • @ прячет команду, но не ошибки
Демо: snippets/01-tabs, 02-phony (mkdir test), 03-one-shell-per-line. А также step-1 проекта: mkdir test && make test и make logs с потерянным cd.

step-2 · фундаментФайлы ваши, а не root

UID ?= $(shell id -u)
GID ?= $(shell id -g)
export UID GID            # → build args образа

# -T, когда нет терминала (CI, пайпы)
TTY  := $(shell [ -t 0 ] || echo -T)
EXEC := docker compose exec $(TTY) app

artisan: ## make artisan C="make:model Post"
	$(EXEC) php artisan $(C)
# Dockerfile
ARG UID=1000
ARG GID=1000
RUN addgroup -g "${GID}" app \
 && adduser -D -u "${UID}" -G app app
USER app
Пользователь создаётся в образе с вашим UID/GID. Просто exec -u 1000 хуже: в контейнере нет такого пользователя, нет HOME, у composer проблемы с кэшем. TTY-детект позволяет одному Makefile работать и в терминале, и в CI без «the input device is not a TTY».

step-2 · нулевой онбордингmake init и авто-справка

.DEFAULT_GOAL := help

help: ## Show this help
	@grep -hE '^[a-zA-Z_.-]+:.*?## ' $(MAKEFILE_LIST) \
	  | awk 'BEGIN {FS = ":.*?## "}; \
	    {printf "\033[36m%-12s\033[0m %s\n", $$1, $$2}'

.env:                     # файловая цель
	cp .env.example .env

init: .env up vendor/autoload.php ## First run
	@grep -q '^APP_KEY=base64' .env \
	  || $(EXEC) php artisan key:generate
	$(EXEC) php artisan migrate --seed
  • make без аргументов = справка из комментариев ##
  • .env создаётся, только если его нет
  • init идемпотентен: второй запуск не меняет APP_KEY и не падает на сидере
  • Не делайте .env: .env.example: перезатрёт ваш .env
Новичок пишет make init и через пару минут пишет код. Почему важна идемпотентность: key:generate в local молча перегенерирует ключ, и слетят сессии и всё, что зашифровано.

step-3 · инкрементальностьСтавим зависимости, только когда нужно

vendor/autoload.php: composer.json composer.lock
	$(EXEC) composer install
	@touch $@                # $@ = имя цели

# npm сам пишет этот файл при каждом install: бесплатный маркер
node_modules/.package-lock.json: package.json $(wildcard package-lock.json)
	$(NODE) npm install
  • Переключились на ветку с новым пакетом → make init сам поставит зависимости
  • Второй раз: make -n init показывает, что composer install не нужен
Демо: make -n init, потом touch composer.lock && make -n init.

step-3 · прощай, nvmNode тоже в контейнере

# docker-compose.yml
node:
  image: node:22-alpine
  profiles: ["node"]
  user: "${UID}:${GID}"
  volumes: [".:/var/www/html"]
  ports: ["5174:5174"]
NODE := docker compose run --rm node

dev: node_modules/.package-lock.json
	docker compose run --rm --service-ports \
	  node npm run dev

assets: node_modules/.package-lock.json
	$(NODE) npm run build

Vite: host: '0.0.0.0', hmr: { host: 'localhost' }. Версия Node зафиксирована в одном месте.

Версия Node теперь часть проекта, а не личное дело каждого. Нативные бинарники собираются под Linux, как и в CI.

step-3 · скорость и защитаПараллельные проверки и «защита от дурака»

ifneq ($(filter output-sync,$(.FEATURES)),)
MAKEFLAGS += --output-sync=target
endif

check: lint stan test ## make -j3 check

db-fresh: ## asks first; FORCE=1 skips
	@printf '\033[31mWipes the DB\033[0m\n'
	@[ "$(FORCE)" = 1 ] || { printf 'Continue? [y/N] '; \
	  read ans; [ "$${ans:-N}" = y ]; }
	$(EXEC) php artisan migrate:fresh --seed
  • make -j3 check: Pint, PHPStan, тесты одновременно, вывод не перемешан
  • В демо: ≈1.3 с вместо ≈3 с
  • FORCE=1 для скриптов и CI
  • .FEATURES: на macOS make 3.81, у него нет --output-sync
Демо: snippets/06-parallel: 3 с против 1 с. Потом echo n | make db-fresh.

step-4 · идеалСтрогий режим и позиционные аргументы

SHELL := bash
.SHELLFLAGS := -eu -o pipefail -c
.DELETE_ON_ERROR:
MAKEFLAGS += --warn-undefined-variables

# make artisan migrate:status · make test UserTest
PROXIES := artisan composer test npm
ifneq ($(filter $(firstword $(MAKECMDGOALS)),$(PROXIES)),)
ARGS := $(wordlist 2,$(words $(MAKECMDGOALS)),$(MAKECMDGOALS))
%:
	@:
endif

🪖 Военная история

Первая версия у нас объявляла аргументы в .PHONY: $(ARGS).

make artisan migrate:status →
multiple target patterns. Stop.

make прочитал двоеточие как «цель: зависимость». Фикс: catch-all %: ; @:.

pipefail: mysqldump | gzip больше не «успешен» при упавшем дампе. DELETE_ON_ERROR: недописанный файл-цель удаляется, а не считается готовым. История реальная, из ревью нашего Makefile.

step-4 · один источник правдыТе же команды у людей и в CI

ci: ## What CI runs
	$(MAKE) init
	$(MAKE) -j3 check

-include Makefile.local   # личное, в .gitignore

doctor: ## docker? compose v2? ports free?
# .github/workflows/ci.yml
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make ci

Никаких setup-php/setup-node: CI поднимает тот же Docker, что и вы.

«В CI зелёное, у меня красное» исчезает, когда CI буквально зовёт ту же цель. make doctor проверяет машину до того, как человек пойдёт читать логи.

Где make не надоГраницы и подводные камни

  • include .env: кавычки остаются в значении, $ съедается make → лучше брать креды из окружения контейнера
  • Сложная логика (циклы, JSON, ветвления) → scripts/*.sh, а make только зовёт
  • macOS: make 3.81 (2006 г.) → проверки .FEATURES или brew install make
  • Windows: только WSL2, проект внутри Linux-ФС, не в /mnt/c
  • Альтернативы: just, Task (go-task): приятнее синтаксис, но их надо ставить
Демо: snippets/05-include-env: APP_NAME с кавычками, пароль pa$word превращается в paord.
